# 작업 A — Speech 모듈 개선

**브랜치: `speech-model`**  (다른 브랜치면 먼저 알려줘)

## 목표
단순 튜닝이 아니라 "기존 모델 진단 → 새 데이터/새 방식으로 재구축 → 기존 대비 얼마나 나아졌는지 증명".

## ⚠️ baseline 전략 (중요 — 2026-09-16 변경)
기존 모델 아티팩트(`rf_pipe.joblib` 등)를 확보할 수 없다. 옛 모델을 로드해서 비교하는 방식은 폐기.
대신 **`preprocess.py`의 기존 feature 레시피 + RandomForest를 새 데이터셋에 직접 재학습해서 baseline으로 삼는다.**
같은 데이터 / 같은 split / 같은 seed에서 비교해야 공정하고, 포트폴리오 설득력도 더 높다.
기존 Accuracy 0.854는 "이전 프로젝트 보고값"으로만 인용하고 직접 비교하지 않는다.

## 평가 기준
의료/이상탐지 도메인이라 **미탐지(실제 언어장애를 정상으로 판단)를 줄이는 게 최우선**.
Accuracy보다 **Recall 우선**.

## 진행 방식
`CLAUDE.md`의 "함께 일하는 방식" 규칙을 그대로 따른다. 페어 프로그래밍 멘토 역할.
**각 단계는 내가 "다음"이라고 할 때까지 절대 넘어가지 말 것.**
단계가 끝나면 `.claude/PROGRESS.md`의 작업 A 체크박스를 갱신해줘.

## 단계
1. **[현재 모델 분석]** 리포 안 Speech 모듈 코드(전처리, feature 추출, 학습, 추론)를 읽고 현재 구조와 데이터 흐름 설명. 어떤 데이터로 학습됐는지도 파악.
2. **[장단점 진단]** 현재 방식(16kHz + MFCC/ZCR/RMS + Random Forest)의 장점과 한계 정리. 특히 "왜 이 접근이 언어장애 탐지에서 한계가 있을 수 있는지"를 데이터 양/편향, feature 표현력, 모델 선택 관점에서 구체적으로.
3. **[방향 결정]** 아래 세 갈래의 장단점·난이도·예상 소요를 표로 정리 → 내가 고른다.
   - (A) 기존 feature 기반 유지, 데이터/모델만 개선
   - (B) 새 데이터셋으로 처음부터 재구축 (classical ML)
   - (C) 새 데이터셋 + 딥러닝 (스펙트로그램+CNN, 또는 wav2vec2 등 사전학습 모델 fine-tuning)
4. **[새 데이터셋 탐색]** 선정 기준부터 같이 세운다 — 한국어 우선(서비스 도메인 일치), 정상/언어장애(구음장애) 라벨 유무, 라이선스(포트폴리오·공개 배포 가능 여부), 데이터 양과 클래스 균형. AI Hub / Kaggle / 논문 부속 데이터셋을 어떻게 찾는지 알려주고, 후보가 나오면 기준으로 같이 평가. **데이터는 내가 직접 찾는다.**
5. **[EDA + 전처리]** 내가 직접 데이터를 뜯어보도록 EDA 방향 제시(클래스 분포, 길이/샘플레이트, 노이즈, 라벨 품질). 그다음 전처리 파이프라인을 하나씩 내가 구현하게 안내.
6. **[모델링]** 3번에서 고른 방식으로 내가 직접 구현. 재현성(seed 고정, train/val/test split 고정)을 처음부터 챙기게.
7. **[학습 & 튜닝]** 학습 루프와 하이퍼파라미터 튜닝을 내가 돌리고, 결과 읽는 법 안내. 클래스 불균형 처리, threshold 조정도 이 단계에서.
8. **[baseline 비교 평가]** 재학습한 RF baseline vs 새 모델을 **같은 test set**으로 비교. confusion matrix, Recall / Precision / F1. "무엇이 왜 좋아졌는지"를 포트폴리오에 쓸 수 있게 정리.
9. **[서비스 적용]** 새 모델을 FastAPI 추론 코드에 교체 적용 (모델 파일 로딩, 입력 전처리 일치, 응답 포맷 유지). 서비스 정상 동작까지 내가 직접 연동.

## 완료 후
9단계까지 끝나면 전체 동작 테스트 → `main`으로 병합 → 그 다음에 `/deploy` 시작.
