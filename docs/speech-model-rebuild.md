# Speech 모듈 재구축 — 음성 기반 구음장애 판별

> F.A.S.T 뇌졸중 경고 서비스의 Speech 모듈을 재구축한 기록.
> 기간 2026-09 ~ 10 / 담당 영역: 모델 재설계 + 서비스 연동

## 요약

졸업 프로젝트의 Speech 모듈은 **학습된 모델 파일이 남아 있지 않아 성능을 재현할 수도, 검증할 수도 없는 상태**였다.
기존 feature 레시피(MFCC + DTW 기반 10개 feature)를 설계도 삼아 공개 데이터셋에 재학습해 비교 기준을 만들고,
사전학습 음성 모델(wav2vec2) 기반으로 재구축했다.

| | 옛 레시피 (동일 조건 재학습) | 새 모델 |
|---|---|---|
| 입력 표현 | 10 feature (DTW 5 + 기울기 + ZCR/RMS 4) | wav2vec2 layer 8, 768차원 |
| ROC-AUC | 0.562 | **0.818** |
| Recall | 0.800 (사실상 전부 양성) | **0.777** |
| 정확도 | 0.429 | **0.726** |
| 미탐지(FN) | 198 | 221 |
| 오탐(FP) | 938 | 325 |

평가는 **화자 단위 5-fold 교차검증 + OOF 풀링**으로 했다. 같은 데이터·같은 split·같은 seed.

서비스 코드는 **778줄 → 385줄**로 줄었다. 학습과 어긋나던 전처리와, 모델 출력을 덮어쓰던 후처리 규칙 250줄을 걷어낸 결과다.

## 1. 배경 — 왜 튜닝이 아니라 재구축인가

인수인계받은 상태를 코드로 확인한 결과:

- **모델 아티팩트(`rf_pipe.joblib`, `dtw_refs.pkl`) 확보 불가.** 보고된 Accuracy 0.854를 재현·검증할 방법이 없었다.
- **학습 스크립트 없음.** 전처리 코드(`preprocess.py`)만 남아 있었다.
- 추론 엔드포인트에 **후처리 가드가 7겹(약 250줄)** 붙어 모델 확률을 덮어쓰고 있었다. 환경변수로 켜고 끄는 매직넘버가 하드코딩돼 있었다.

측정할 수 없으면 개선도 증명할 수 없다. 재구축이 유일한 선택이었다.

> 주의: "가드가 250줄이니 모델이 나쁘다"는 직접 증거가 아니다. 가드는 증상이지 측정값이 아니다.
> 재구축의 근거는 **"재현 불가 → 측정 불가"**이고, 가드는 그 동기로 인용한다.

## 2. 기존 모델 진단

코드를 읽어 복원한 파이프라인:

```
16kHz → pyin 유성구간 concat → 최에너지 10초 크롭 → 5등분
      → 조각별 MFCC 13차 + CMVN
      → 정상 참조 음성과 DTW → 거리 5개 + 기울기 1개
      → ZCR/RMS 평균·표준편차 4개
      = 10 feature → RandomForest
```

**핵심 한계 두 가지**

1. **표현 병목.** 10초 × 13차 × 약 600프레임(≈8,000개 값)이 숫자 10개로 압축된다. MFCC는 모델 입력이 아니라 DTW 거리 계산용 중간산물일 뿐이다.
2. **데이터 수집 프로토콜과의 강한 결합.** DTW는 "정해진 문장을 읽은 참조 음성"과 비교하는 구조다. 프론트엔드가 고정 자기소개 문장을 제시하고, `dtw_refs.pkl`이 그 문장의 정상 발화를 담고 있었다. 프롬프트를 바꾸면 참조를 다시 수집해야 한다.

또한 서빙 코드에만 추가된 변경(`pyin` VAD, "중앙 크롭 → 최에너지 크롭")이 있어 **학습-서빙 불일치(train/serve skew)** 가능성이 있었다.

## 3. 데이터셋 선정 — 감수한 트레이드오프

| 후보 | 결과 |
|---|---|
| AI Hub 구음장애인 명령어 데이터 (한국어, 뇌졸중) | ❌ **온라인 안심존 전용.** 외부 데이터 반입·모델 가중치 반출이 모두 불확실. 정상 대조군도 미포함 |
| **TORGO** (Rudzicz et al. 2012) | ✅ **채택** |

TORGO를 고른 결정적 이유는 **matched control**이다. 환자와 대조군을 같은 연구실·같은 장비로 녹음했기 때문에, "모델이 병리가 아니라 녹음 환경을 학습하는" shortcut이 구조적으로 막힌다. 한국어 코퍼스에서 정상 음성을 따로 가져왔다면 이 함정에 빠졌을 것이다.

**감수한 한계** — 영어 발화이고, 병인이 뇌성마비·ALS로 뇌졸중이 아니다. 배포 파이프라인(후속 작업)이 이 모델 산출물에 의존하므로, **도메인 일치보다 완주 가능성을 우선**했다.

구성: 화자 15명(구음장애 8 / 정상 7), 2,000 샘플, 클래스·성별 균형, 전부 16kHz.

## 4. EDA — 집계 단위가 결론을 뒤집은 사례

**"구음장애 화자의 발화가 더 긴가?"**

| 집계 단위 | 결과 |
|---|---|
| 발화 단위 (n=1,999) | 구음장애가 평균 **32% 김** (3.56s vs 2.69s) |
| 화자별 중앙값 (n=15) | **차이 9%**, 분포가 완전히 섞임 |

화자별로 보면 최단이 구음장애(F01 1.73s), 최장이 정상(FC01 3.30s)이었다. 발화 단위 차이는 특정 화자(F03, 292개)와 긴 꼬리가 만든 것이었다.

**→ 길이는 라벨을 누출하지 않는다**(shortcut 위험 낮음)는 결론을 채택했다. 화자별 발화 수가 7.5배까지 차이나는 데이터에서 발화 단위 평균은 믿을 수 없다.

부수 발견: 진짜 차이는 평균이 아니라 **분산**이었다(std 2.88 vs 1.30).

그 외 정리한 것 — 샘플레이트 전부 16kHz 단일(리샘플링 불필요), 0바이트 파일 1건 제외, 0.3초 미만 8건 제외(전부 한 화자의 녹음 사고).

## 5. 모델링 — 기각한 가설 2개, 검증한 가설 1개

인코더는 freeze하고 임베딩만 1회 추출한 뒤 가벼운 분류기를 올렸다. 하드웨어 제약(Intel Mac, CPU)과 일정상 full fine-tuning은 비현실적이었다.

**평가 설계**

- **화자 단위 split이 필수.** 화자를 섞으면 모델이 "구음장애의 특징"이 아니라 "이 사람의 목소리"를 외운다. 이 데이터셋의 공개 노트북 상당수가 95%+를 보고하지만 대부분 화자 누수가 있다.
- `StratifiedGroupKFold`는 **이 데이터에서 쓸 수 없었다.** 화자 1명이 전부 한 클래스라 발화 단위 층화 제약이 충족 불가능해지고, 한 클래스만 담긴 fold가 생겼다(Recall 계산 불가). **화자 수준에서 층화**하도록 바꿨다.

**기각 ① — 과적합 가설.** 정규화를 강화할수록(C: 1 → 0.0001) AUC가 단조 하락했다. PCA도 전부 기본값보다 낮았다.

**기각 ② — 하이퍼파라미터 튜닝.** 중첩 교차검증에서 fold별로 고른 C가 0.0001~1로 널뛰었고, 그 결과가 **고정값보다 나빴다**(AUC 0.619 vs 0.710). 내부 fold에 화자가 4~5명뿐이라 안정적 선택이 불가능하다. → **튜닝하지 않고 기본값 고정**. 선택 과정이 없으므로 보고 수치에 selection bias가 없다.

**검증 — 표현 가설.** 13개 레이어 × 3가지 풀링 39조합을 비교했더니 AUC가 뚜렷한 역U자를 그렸다.

```
layer  0 : 0.629        layer  8 : 0.818  ★
layer  4 : 0.741        layer 10 : 0.773
layer  6 : 0.787        layer 12 : 0.710   ← 마지막 레이어
```

마지막 레이어가 최악에 가깝다. wav2vec2의 사전학습 과제(마스킹된 양자화 단위 예측)가 상위 레이어에서 프레임별 변동을 눌러 문맥적으로 안정된 표현을 만들기 때문으로 보인다. 실제로 레이어 11·12에서 시간축 표준편차가 0.19 → 0.12로 급락했다.

> EDA에서 "분산이 신호"라는 관찰이 있어 std 풀링도 넣어봤으나, **최적 레이어에서는 mean 단독이 더 좋았다**(Recall 0.727 vs 0.710). 하위 레이어에서만 유효했던 부분적 직관이었다.

**임계값 0.15** — 기본 0.5 대비 미탐지 271 → 221건. 대가는 오탐 212 → 325건. 의료 스크리닝에서 "환자를 정상이라 판단"하는 비용이 더 크다고 보았다. 효과가 경증 화자에 집중된 것(F03 0.226 → 0.401)도 의도한 방향이었다.

## 6. baseline 비교 — 과대 주장을 피하기

옛 레시피를 **같은 데이터·같은 fold·같은 seed**로 재학습했다. DTW 참조는 **각 fold의 train 정상 화자에서만** 뽑았다(전체에서 뽑으면 test 화자가 feature에 새어들어 화자 독립 평가가 무의미해진다).

결과는 AUC 0.562로 거의 무작위 수준. thr=0.15에서 Recall 0.800이 나오지만, **정상 1,000명 중 938명을 오탐**한 "전부 양성" 분류기의 수치다.

**다만 이 비교는 baseline에 불리하다.** DTW는 고정 프롬프트를 전제하는데 TORGO는 서로 다른 단어/구다. 참조와 내용이 애초에 다르니 10 feature 중 6개가 사실상 노이즈가 된다.

**그래서 정직한 결론은 둘이다.**

1. 옛 레시피는 이 데이터셋에서 판별력이 거의 없다.
2. 그 원인의 상당 부분은 **레시피가 데이터 수집 프로토콜에 강하게 결합돼 있기 때문**이다.

(2)가 더 중요한 성과다. 옛 모델은 고정 프롬프트와 그 프롬프트의 참조 음성이 있어야만 작동한다. 실제로 참조가 없을 때 상수 4.5로 때우는 fallback이 코드에 있었다 — 취약성을 코드가 이미 인정하고 있었다. **새 모델에는 그 전제가 없다.**

## 7. 서비스 연동

```
bytes → 디코딩(webm/mp3/wav) → 입력 검증 → wav2vec2 임베딩 → 분류기 → 판정
```

- **학습-서빙 전처리 일치를 최우선으로 확인했다.** 저장된 학습 임베딩과 서비스가 만든 임베딩을 비교해 **최대 차이 0.00e+00**(비트 단위 일치)을 확인한 뒤 나머지를 진행했다.
- **VAD / 10초 크롭 / 타일링 제거.** 학습 입력에 없던 단계다. 남겨두면 측정한 성능이 무효가 된다.
- **후처리 가드 7겹 삭제.** DTW feature를 전제하므로 새 모델에서 동작 자체가 불가능했다.
- **모델 경로·버전·임계값을 환경변수로 주입.** 설정을 바꿔 판정이 뒤집히는 것까지 확인했다(`SPEECH_THRESHOLD=0.01` → 같은 risk, 판정만 반전).
- `meta.json`을 **서빙 계약서**로 두었다. 레이어·풀링·샘플레이트·임계값·전처리 규칙·기대 성능이 모델 파일과 함께 다닌다. 인수인계 때 겪은 문제의 반대 조치다.

### 실사용 테스트에서 발견한 오동작

브라우저 녹음으로 테스트하다 **아무 말도 하지 않은 10초 녹음이 0.97로 Abnormal 판정**되는 것을 발견했다.

원인은 **모델에 "발화 아님" 클래스가 없다**는 것. 구음장애/정상 둘 중 하나로만 학습됐으므로 학습 분포 밖의 입력은 억지로 한쪽에 배정된다. 잡음은 조음 구조가 없어 중증 구음장애 영역에 가깝게 떨어진다.

RMS로는 걸러지지 않았다(무음 녹음 0.0252는 실제 발화의 상위 9% 지점). **스펙트럼 평탄도**로 양방향 게이트를 만들었다.

```
TORGO 실제 발화 249개    0.00067 ~ 0.05817
백색잡음 0.5615 ↑         60Hz 험·순음 0.0000 ↓
→ 허용 범위 0.0002 ~ 0.15
```

게이트에 걸리면 **모델을 돌리지 않고** `risk: null`, `decision: "Abnormal"`, `reason: "no_speech_detected"`를 반환한다. 말을 하지 못하는 상태 자체가 경고 신호이므로 판정은 유지하되, **근거 없는 확률을 보여주지 않는다.** 옛 코드가 무음일 때 확률을 0.65로 끌어올리던 방식과는 다르다.

#### "무음은 Abnormal" 은 원래 우연이었다

게이트를 넣기 전 비발화 입력 4종을 모델에 직접 통과시켜 보았다.

| 입력 | risk | 판정 |
|---|---|---|
| 백색잡음 | 0.00013 | Normal |
| 60Hz 험 | 0.0000082 | Normal |
| 440Hz 순음 | 0.00117 | Normal |
| 핑크잡음 | 0.99999 | **Abnormal** |

같은 "발화 아님" 입력인데 **4개 중 3개가 Normal** 이었다. 처음 관찰한 "무음 → 0.97 Abnormal" 은 잡음 종류가 우연히 그렇게 떨어진 결과였을 뿐, 모델이 "말을 하지 못함" 을 탐지한 것이 아니었다. 모델의 우연에 맡기지 않고 **게이트로 의도적으로 판정**해야 하는 이유다.

#### 게이트가 막지 못하는 것 — 실측

실제 카페에서 13.62초를 녹음해 올렸더니 **게이트를 통과해 `risk 0.9999 / Abnormal`** 이 나왔다.

카페 소음에는 사람 목소리가 섞여 있어 배음 구조를 가지므로 평탄도 게이트에 걸리지 않는다. 그리고 모델은 "누가 말했는지" 를 구분하지 않는다. 원거리의 불명확한 음성은 조음이 흐릿해 중증 구음장애와 유사하게 보인다.

**이는 "조용한 환경에서 녹음" 이라는 사용 전제를 요구한다.** 그러나 뇌졸중 의심 상황은 대개 조용하지 않다(길거리, 식당, 가족이 곁에 있는 상황). 해결하려면 화자 분리 또는 근접 발화 검출이 필요하고, 학습 데이터가 녹음실 음성(TORGO)뿐이라 현 단계에서는 불가능하다. 후속 과제로 남긴다.

## 8. 운영 환경 정비 — 비밀정보 노출 대응

작업 중 **공개 저장소에 비밀정보가 커밋돼 있는 것**을 발견했다.

| 위치 | 노출 항목 |
|---|---|
| `back-end/.env` (git 추적 중) | `SECRET_KEY`, `DB_USER`, `DB_PASSWORD` |
| `docker-compose.yml` | `MYSQL_ROOT_PASSWORD`, `MYSQL_PASSWORD` 평문 |

저장소는 public 이고 포크가 2개 존재했다. **포크된 사본에는 히스토리 재작성이 미치지 않으므로, "지우기" 가 아니라 "값을 무효화하기" 를 우선**했다.

**조치 순서**

1. **값 전면 교체** — `SECRET_KEY`(64자 재생성), DB 비밀번호, MySQL root 비밀번호. 노출된 값을 죽은 값으로 만드는 것이 유일한 확실한 조치다.
2. **`.env` 추적 해제** — `.gitignore` 추가 + `git rm --cached`. 대신 `.env.example` 을 커밋했다. 비밀값 2개는 비우고, 더 이상 읽히지 않는 옛 설정 35개는 "사용 안 함" 주석으로 남겨 이력을 보존했다.
3. **`docker-compose.yml` 을 참조 방식으로 변경** — 평문 대신 `${DB_PASSWORD}` 형태. compose 가 `.env` 를 읽도록 루트에 심볼릭 링크를 걸었다.
4. **히스토리 재작성은 하지 않음** — 포크에 남아 효과가 제한적이고, 모든 커밋 SHA 가 바뀌어 포크와 어긋난다. 값 무효화로 충분하다고 판단했다.

**이 과정에서 겪은 것** — `.env` 만 교체하고 `docker-compose.yml` 을 놓쳐 DB 연결이 끊겼다. 같은 값을 두 곳에 두면 반드시 어긋난다. 설정을 한 곳(`.env`)으로 모으고 나머지는 참조만 하도록 바꾼 이유다. 이 경험은 이후 Kubernetes `Secret` 설계로 이어진다.

## 9. 한계와 후속 과제

| 한계 | 내용 |
|---|---|
| **도메인 불일치** | 영어 발화, 병인이 뇌성마비·ALS. 한국어 뇌졸중 데이터로 검증하지 못했다 |
| **경증 탐지 실패** | 중증 화자는 거의 완벽(M01/M02/M04 ≈ 1.00)하나 경증 F03은 0.401. 경증 화자가 train에 2~3명뿐이라 데이터 수준의 한계로 보인다 |
| **표본 크기** | 화자 15명. 하이퍼파라미터조차 안정적으로 고를 수 없었다. fold별 Recall 0.871 ± 0.186 |
| **발화 게이트의 범위** | 광대역 잡음·순음만 막는다. **카페 녹음 13.62초가 통과해 0.9999 Abnormal 로 오탐되는 것을 실측 확인.** 조용한 환경을 전제한다 |
| **baseline 비교의 공정성** | DTW가 고정 프롬프트를 전제하므로 TORGO에서 불리하다. 전사 텍스트가 없어 "같은 프롬프트 참조" 실험은 하지 못했다 |

후속 과제: OOD 탐지 또는 "발화 아님" 클래스 추가, **잡음 환경 대응(화자 분리·근접 발화 검출)**, 한국어 데이터 확보 시 재검증, 모델 레지스트리(MLflow)를 통한 버전 관리.
